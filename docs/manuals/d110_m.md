# NIIMBOT D110_M

What is known about the D110_M, the model this bench was first pointed at. It is a D110 in a different case with a different firmware, and the difference that matters here is the radio: **the D110_M is reached over BLE only.** A manual for the D110 covers the same roll, indicator, and pairing, so [d110.md](d110.md) is the user-facing page and this one is the model's own facts. The index is [README.md](README.md).

## Model

| Parameter | Value |
|---|---|
| Model id | `2320` |
| Resolution | 203 dpi |
| Printhead | 12 mm / 96 dots |
| Density range | 1–5, default 3; niimbench's `d110_m` model offers all five ([../subsystems/printer.md](../subsystems/printer.md#models)) |
| Paper types | gap (1) and transparent (5) |
| Printer type | thermal |

The model id is what `PrinterInfo` key `0x08` answers with, and it is the number [../subsystems/printer.md](../subsystems/printer.md) maps onto a head.

## Bluetooth

The printer puts its print channel under the vendor service `e7810a71-73ae-499d-8c15-faa9aef0c3f2`, characteristic `bef8d6c9-9c21-4c9e-b632-bd58c1009f9f`, which carries `read`, `write`, `write-without-response`, and `notify` and reports a 244-byte MTU.

It does **not** offer the Serial Port Profile and its low energy advertisements set the `BR/EDR Not Supported` flag, so there is no Classic radio and no RFCOMM channel 1 to reach it on. A caller that opens `AF_BLUETOOTH`/`BTPROTO_RFCOMM` against either of the two addresses the printer advertises gets `EHOSTDOWN` after about eight seconds. The frames are the same `55 55 … aa aa` packets the serial printers take; on this model they travel as GATT writes, and the replies come back as notifications, which BlueZ caches in the characteristic's `Value` property.

The two addresses the scan reports are the public `C4:17:82:12:34:56` and the reversed `04:17:82:56:34:12`; both belong to the same unit, and neither answers Classic.

## What the printer will not tell you

This unit was asked for its roll directly, which is the obvious way to learn a label's size instead of making the caller state it. `RfidInfo` (`0x1a`) answers 39 bytes carrying the roll's barcode `01222281` and serial `PZ1I609450000809` and nothing about its geometry, and `GetPaperInfo` (`0x59`) answered `00 18 00 18` on a 12×40 gap roll — 24 mm, which is neither dimension of the roll that was loaded, so the printer is not reporting the measurement.

The gap sensor is what positions this printer, and the printer uses the tag internally for gap calibration on power-on and lid close. It does not send the dimensions over the protocol; the vendor app looks the barcode up in the cloud. So a caller that prints to this model has to know its page size: niimbench reads the barcode and looks it up in the roll catalogue compiled into it ([../subsystems/http.md](../subsystems/http.md#the-roll)). The gap sensor is also why a print stops short of the label by a margin ([../subsystems/printer.md](../subsystems/printer.md#raster)).

## Protocol

Asked with `Connect` and `PrinterStatusData`, this unit answers protocol version 4 (`n = 301`). The print sequence for that version tells the printer the job's page count and the page's copy count. Sent the older D110 sequence, which tells it neither, the unit now and then printed a label twice, both copies whole, even with `PrintQuantity` set to 1. The sequences are in [../subsystems/printer.md](../subsystems/printer.md#wire).

## Clock

The unit has a date button that prints its own clock, which reads 1970 until something sets it. `PrinterConfig2` sets it in the form the protocol notes draw, `01` and then the date, which it answers `01 01`. Upstream's library puts an item byte `08` in front; this unit refuses that with `08 00`. The route is in [../subsystems/http.md](../subsystems/http.md#label-body).

## Capabilities

`GetPrinterCapabilities` (`0xAF`, answered `0xBF`) lists what the firmware supports as type-length-value fields ([upstream/interfacing/proto.md](upstream/interfacing/proto.md#getprintercapabilities)). Asked on 2026-10-29, firmware 4.30 on hardware 4.01, this unit answers fields `0x01` to `0x19` and none after them. The ones that matter here:

| Field | Answer | Means |
|---|---|---|
| `0x04` PrintheadDpi | `00 c8` | 200, the 203 dpi class |
| `0x07` DensityRange | `05 01` | density 5 to 1 |
| `0x08` SpeedRange | `05 01` | speed 5 to 1 |
| `0x0a` PrintheadWidth | `00 60` | 96 dots |
| `0x0b` MaxPrintHeight | `06 40` | 1600 dots, 200 mm |
| `0x17` RealTimeClock | `01` | it keeps a clock |
| `0x1a` PrintColor | not listed | one ink |
| `0x20` SixteenGrayMaxBuffer | not listed | no 16-level grey mode |

niimbench does not ask for this; the answer above came from a one-off read.

## Firmware

`PrinterInfo` answers firmware `04 1e`, 4.30, for key 9 and hardware `04 01`, 4.01, for key 12; `POST /api/printer/info` reads both ([../subsystems/http.md](../subsystems/http.md)). The microcontroller is a YiChip YC3122-L, and the firmware image's layout is in [upstream/hardware/niimbot-d110_m.md](upstream/hardware/niimbot-d110_m.md). The unit refuses an image older than the one it runs ([upstream/firmware/flashing-firmware.md](upstream/firmware/flashing-firmware.md#downgrading-firmware)), so one built on 4.31 is the oldest it takes from 4.30.

The firmware has been changed and flashed over Bluetooth before: [pranavms13/niimbot-d110m-patched-firmware](https://github.com/pranavms13/niimbot-d110m-patched-firmware) patches 4.31 on hardware 4.01 to clear the printer's memory of rolls, with a hash-pinned patch builder and a Bluetooth flasher. niimbench uses none of it; it is where a firmware change to this model would start.

## Grayscale

This unit prints no greys of its own, and every grey in a picture is made of dots: the editor's dithering ([../user/guide/index.md](../user/guide/index.md#place-a-field)).

The head is a row of 96 heating resistors, one per dot. For each line the firmware shifts in one bit per dot, then fires one strobe pulse, whose length follows **Density**; a dot whose resistor is on turns black. One bit per dot, and one heat for the whole job, is the whole of what the protocol and this firmware offer.

A thermal printer prints grey with the same head and several shorter pulses per line. The firmware loads the line once for each sub-pulse, each time switching on only the dots that still need heat, so a dot's total time on, and so its darkness, follows its grey level: 16 levels are 4 bits per dot and up to 15 sub-pulses. Some Niimbot models do this, which is what the `SixteenGrayMaxBuffer` capability says; this unit does not list it. Nothing in the head prevents it: it is the firmware's timing.

A grey mode on this unit takes:

1. **Firmware.** There is no source, so the vendor image is patched.
   - A print-row command that carries 2 or 4 bits per dot, about 48 bytes for a 96-dot line at 4 bits.
   - The print loop, found in the image: per line, load and strobe once per sub-pulse, each on-time calibrated against the paper.
   - Heat history: a dot that was on in the line before darkens sooner, so on-times are shortened after it, or the greys come out blotchy.
   - `0x20` added to the capabilities answer, so a client can tell the mode is there.
   - Built on 4.31 or later, flashed as the patch above is.
2. **niimbench**, once a firmware offers it:
   - ask `GetPrinterCapabilities` and offer grey when `0x20` is listed;
   - in the page, send a picture's tones as grey levels instead of dots: `pictureDots` and `backgroundPixels` in [../../src/editor.html](../../src/editor.html);
   - on the server, pack 4 bits per dot instead of one: `raster.packRow` in [../../src/raster.zig](../../src/raster.zig), from the grayscale the renderer already draws;
   - in the printer client, send the grey row command in place of `PrintBitmapRow` in the print sequence in [../../src/printer.zig](../../src/printer.zig).

The limits are the paper's and the head's. Direct thermal paper turns from white to black over a narrow temperature range, so the greys it can hold are few, and they shift with the room's temperature and with how hot the head already is; at 203 dpi a halftone often looks as good. A pulse too long burns out head elements, and a failed flash can leave the printer unable to boot.
